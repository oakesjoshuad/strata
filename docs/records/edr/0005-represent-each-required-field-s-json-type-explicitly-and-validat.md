# EDR-0005: Represent each required field's JSON type explicitly and validate it

## Context

records/src/kind.rs's default_document() decides whether a required field is scalar (JsonValue::String) or list-shaped (JsonValue::Array) using a hardcoded if/else chain over field-name string literals. That chain is the only place this type information exists as a declaration; everywhere else that needs it either duplicates the list or infers it indirectly. cli/src/parse.rs's array_field() is one such indirect consumer: to determine whether a Markdown section should parse as a list, it calls kind.default_document("") and inspects the JSON type of the resulting placeholder value for that field, rather than consulting a real declaration. Issue #10's review found the concrete cost of this: nothing declares that, say, 'motivation' must be a string and 'alternatives' must be an array, so records/src/validation.rs's validate_document() had no way to check it, and a record whose 'motivation' field held Array([]) (the wrong type entirely, not just an empty value) passed validation as though it were valid content. During implementation, a full audit of the real self-hosted database (all 20 records at the time) found that the original List classification itself was wrong: every field default_document() marked as List -- alternatives, evidence, requirements, constraints, non_goals, questions_for_review, components, interfaces, failure_modes, experiments, risks, open_questions, resulting_decisions -- is, in every single real record, authored as a prose string (often containing embedded Markdown bullet or bold-heading syntax within the string), never as a genuine JSON array, with zero exceptions across two independent authoring processes (the original hand-migration in #4, and this project's own CLI-authored RFC-0002 record set). This project's revision history now records that finding as evidence, not as an assumption: this decision's first accepted revision claimed the corpus already conformed to the List/Scalar split; that claim was verified false before implementation shipped.

## Decision

We will add an explicit, authoritative field-type declaration to RecordKind: a FieldKind enum (Scalar, List) and a function pairing each of a kind's required_fields() with its FieldKind, replacing the implicit knowledge currently duplicated across default_document()'s if/else chain and array_field()'s document-construction inference. default_document() and array_field() are both rewritten to read from this one table instead of their own separate logic. validate_document() gains a new check: for every required field, the document's JSON value must match its declared FieldKind -- a Scalar field must decode to a non-empty JsonValue::String, a List field must decode to a JsonValue::Array (empty is a legitimate value for a list field, not an error). This subsumes and replaces the existing ad hoc string-emptiness check, which only ever covered the Scalar case by accident. Given the corpus audit in Context: every required field across all four kinds (RFC, PDR, ADR, EDR) is classified Scalar. FieldKind::List remains a real, supported type -- render.rs and parse.rs already handle it correctly and that code is not being removed -- but no required field is currently assigned it. A future field may use List if its real authored content is genuinely list-shaped; none of the current fields are.

## Considered Options

Leave the type list implicit and give validate_document its own separate copy of the field-name list -- rejected, this adds a third duplicated copy of the same knowledge instead of fixing the duplication that caused the bug in the first place. Have validate_document call default_document() and compare JSON types the way array_field() already does -- rejected, this still treats a placeholder-construction function as the source of truth by side effect rather than by declaration. Migrate the real data instead of correcting the classification -- rejected as the general approach: splitting flowing multi-paragraph analysis (alternatives, evidence) into artificial array items matches how none of these fields are actually written, by either author, and would be destructive busywork with no real benefit. One field, RFC's non_goals, was specifically considered for content migration instead of reclassification, since its real content (a one-line intro plus five discrete bullet points) is the closest thing to genuinely list-shaped content in the corpus -- rejected in favor of a single uniform rule (every required field is Scalar) over a special case for one field, since the render/parse pipeline already handles non_goals' embedded bullet syntax correctly as prose and nothing is gained by forcing it into an array.

## Consequences

records/src/kind.rs gains a small FieldKind enum and one authoritative per-kind field-type table, with every required field currently classified Scalar. default_document(), array_field() (cli/src/parse.rs), and validate_document() (records/src/validation.rs) all read from that one table; a future required field only needs its type declared once for all three call sites to behave correctly. No data migration: all 20 real records' content is unchanged, since every field was already authored as prose and is now correctly classified as such. A new ValidationError variant distinguishes 'wrong type' from the existing EmptyField/MissingField cases. If a future field is genuinely list-shaped, FieldKind::List is available and already supported end-to-end (render, parse, template); nothing about this decision requires re-adding that capability later.

## Evidence

Issue #10's review (oakesjoshuad/strata#10): found Array([]) passing validate_document for a field that should have been a non-empty String. Issue #12 (oakesjoshuad/strata#12): filed to track the general gap. A full corpus audit performed during implementation (all 20 records, every required field checked against its declared FieldKind directly against the database) found 53 field-level mismatches across every record with a List-declared field -- 100% of List-declared fields in the corpus, zero exceptions. records/src/kind.rs: default_document()'s hardcoded field-name if/else chain, the source of the original (incorrect) classification. cli/src/parse.rs's array_field(), ADR-0002's alternatives field (a string containing embedded '- **Bold heading**' bullet syntax that already round-trips correctly through render/parse per issue #9's and #11's verification) as a concrete example that the existing string/Paragraph path already handles this content shape correctly. AGENTS.md / CLAUDE.md rule 7: 'A command that turns a bad document into a default or an empty result is a bug' -- the rule this gap violates and this decision closes.
