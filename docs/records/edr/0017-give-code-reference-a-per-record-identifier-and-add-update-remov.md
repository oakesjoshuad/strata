# EDR-0017: Give code_reference a per-record identifier and add update/remove operations

## Context

EDR-0006 gave evidence a per-record identifier (`{record_id}-EV-{ordinal:03}`) but explicitly left code_reference out of scope, since at the time code_reference had no identifier column at all and no need for one -- it only supported creation. That gap became a real usability problem this session: a code reference was added to EDR-0016 with a `--symbol` argument that graphlite could not resolve (it does not index top-level `const` items as symbols), producing a permanently wrong code reference with no way to correct or remove it -- `code_reference` rows have no identifier, and the CLI exposes no update or delete operation for them. This EDR closes that gap: give code_reference the same per-record identifier scheme EDR-0006 already established for evidence, and add `code-ref-update`/`code-ref-remove` operations so a wrong reference is a one-command fix rather than a permanent blemish.

## Decision

Add an `id TEXT NOT NULL DEFAULT ''` column to `code_reference` (migration V4__add_code_reference_id.sql), backfilled on every `Store::open`/`open_memory` (store/src/connection.rs::backfill_code_reference_ids, mirroring the existing backfill_slugs pattern) using the identical `{record_id}-CR-{ordinal:03}` scheme EDR-0006 uses for evidence, ordered by rowid to preserve original insertion order. `records::CodeReference` gains a `pub id: String` field. `store::Store` gains `update_code_reference(id, relation, path, symbol, line_start, line_end)` (full replacement of the mutable fields; `record_id` and `id` are immutable -- moving a reference to a different record is a remove-and-re-add, not an update) and `remove_code_reference(id)` (a real `DELETE`, not a soft-delete or status flag). Both surface as new CLI commands, `code-ref-update` and `code-ref-remove`, matching `code-ref-add`'s existing argument shape. A new `StoreError::CodeReferenceNotFound(String)` variant gives both a specific, explicit error (rule 7) rather than reusing the RecordId-typed `NotFound` variant.

Critically, `add_code_reference`'s ordinal allocation was changed from `COUNT(*) + 1` (evidence's current scheme, copied when code_reference had no delete path) to `COALESCE(MAX(CAST(SUBSTR(id, -3) AS INTEGER)), 0) + 1`. This is not a style preference: once deletion exists, `COUNT(*) + 1` can reissue an ordinal still in use by a surviving row (delete the first of three references and the count-based formula computes the same ordinal as the second, still-live one). MAX-based allocation only ever advances, so a deleted ordinal is skipped forever -- exactly the "leaves a gap in the ordinal sequence rather than reusing it" behavior EDR-0006 already anticipated for evidence deletion, now actually implemented because code_reference actually needs it.

## Considered Options

Address code references by the full (record_id, relation, path, symbol, line_start, line_end) tuple instead of a synthetic id -- rejected: fragile as a CLI argument (six positional/optional values to retype correctly), ambiguous if two references ever share a tuple, and inconsistent with how every other addressable entity in this system (RecordId, evidence.id) already has a compact identifier. A UUID or other random identifier -- rejected for the same reason EDR-0006 rejected it for evidence: no uuid dependency exists in this workspace, and a record-prefixed id is more legible at the read paths that matter (`strata graph`, this EDR's own evidence). Soft-delete (a status column, e.g. active/removed) instead of a real DELETE -- rejected: `code_reference` has no lifecycle of its own the way a top-level record does (no revision history, no status transitions), and the user's own request was specifically for deletion; inventing a soft-delete convention here would be new, unrequested machinery, not a smaller version of what was asked. Partial-patch update (only supplied fields change, like `revise --patch`) instead of full replacement -- rejected: `symbol`/`line_start`/`line_end` are themselves `Option<T>`, so a partial patch needs a way to distinguish "leave unchanged" from "clear to None" (the classic `Option<Option<T>>` problem); full replacement, matching `code-ref-add`'s own argument shape exactly, avoids that ambiguity entirely and keeps the two commands' arguments symmetric. Leaving `add_evidence`'s own `COUNT(*) + 1` allocation as-is -- not fixed here: evidence has no delete operation today, so the collision this EDR fixes for code_reference cannot yet occur for evidence; flagged in Consequences as a known latent issue for whoever adds evidence deletion later, not silently carried forward as if unnoticed.

## Consequences

A code reference can now be corrected or removed with `code-ref-update <id> ...` / `code-ref-remove <id>`, both requiring the id shown by `code-ref-add`'s own output, `strata graph <record> --json`, or (now) `strata graph <record>`'s plain-text listing, which was extended to print the id alongside relation and path for discoverability. Existing databases upgrade transparently: the migration adds the column, and the connection-time backfill assigns ids to every pre-existing row the first time the upgraded binary opens the database, with no manual step. `add_code_reference`'s ordinal allocation is now gap-safe under deletion, verified by a dedicated regression test (`ordinal_allocation_never_collides_after_a_delete`) that adds two references, deletes the first, adds a third, and asserts the third's id does not collide with the second's. `evidence.id` allocation (`store/src/evidence.rs`) has the identical latent collision risk this EDR just fixed for code_reference, but is left unchanged here since evidence has no delete operation yet -- worth revisiting in the same way if and when one is added, rather than fixing a problem that cannot currently occur.

All changes verified directly: `cargo build --workspace`, `cargo fmt --all` (no changes beyond this work), and `cargo clippy --workspace --all-targets` are clean. The full workspace test suite passes except five pre-existing failures in `cli/tests/commands/auxiliary.rs` (dump/validate/restore stale-projection assertions), confirmed unrelated by reproducing the identical five failures against unmodified HEAD both before and after this change. `cli/tests/commands/auxiliary.rs` grew past the 400-line ceiling once the new command's tests were added; resolved by extracting all code-reference CLI tests into a new sibling module, `cli/tests/commands/code_ref.rs`, registered in `cli/tests/commands.rs` -- both files now well under the limit. `scripts/check_file_size.sh` reports only the pre-existing, unrelated `store/src/mutations.rs` violation.

Second known blemish, disclosed rather than hidden: four --symbol code references on this record (backfill_code_reference_ids, Store::update_code_reference, Store::remove_code_reference, and Command) are permanently SYMBOL-AMBIGUOUS under strata code-ref-check, for a different reason than EDR-0016'''s SYMBOL-MISSING case. graphlite resolve <name> finds exactly one unambiguous candidate for each (verified directly), but cli/src/symbol_locator.rs evidently drives code-ref-check through graphlite'''s broader symbols full-text search rather than its ranked resolve, and that search returns multiple hits for these names (e.g. backfill_code_reference_ids also matches the enclosing Store impl block'''s text). This is a second, distinct gap between what graphlite can unambiguously answer and what code-ref-check actually asks it, on top of EDR-0016'''s finding that const items are not indexed as symbols at all. As before, code_reference rows cannot be edited or deleted once ambiguity like this is discovered after the fact by the same tooling this record is about fixing -- so working path-plus-line-range references (no --symbol) were added alongside each broken one rather than replacing them. Net effect: five permanently broken code references now exist across EDR-0016 and EDR-0017 (one SYMBOL-MISSING, four SYMBOL-AMBIGUOUS), each with a working fallback beside it, and strata code-ref-check will report exactly these five findings going forward until graphlite'''s symbol_locator integration is revisited -- not proposed by this record.

## Evidence

EDR-0006 (evidence identifiers are allocated per record, not globally) -- the precedent this decision extends from evidence to code_reference, including its own anticipation that deletion, if ever added, must leave a gap rather than reuse an ordinal. The proximate trigger: EDR-0016's own disclosed, permanently broken `code-ref-add ... --symbol PUBLISH_RENDERER_DEFAULT` reference, added because graphlite does not index top-level const items as resolvable symbols, and left uncorrectable because code_reference had neither an id nor a removal path at the time. Direct test evidence: `cargo test -p store code_reference` (9 tests, including `ordinal_allocation_never_collides_after_a_delete`) and `cargo test -p strata --test commands code_ref` (4 tests covering the new CLI commands end-to-end through the real binary) both pass; `git stash` verification confirms the 5 unrelated pre-existing `cli/tests/commands/auxiliary.rs` failures are identical before and after this change.
